# Results, data sources and mismatches

Every number below comes from one of: the report (R), the C code in `firmware/` (C), the logged C-simulation run
(`analysis/data/c_sim_simulation.csv`, S-C) or the Python re-implementation (S-Py, `docs/metrics/*.json`, regenerated by
`make figures`). Nothing here was measured on hardware by this repo.

## What is verified, and how

| Claim | Value | Source |

| Closed loop stable with the report's K on the derived plant | max pole magnitude 0.9745 | S-Py (`check_report.json`) |
| Roll pulse response (10 deg, our choice of amplitude) | 10-90 % rise 0.85 s, 2 % settling 1.53 s, no overshoot | S-Py (`response.json`) |

| Disturbance (0.5 rad/s roll-rate kick), roll excursion | 0.14 deg with LQR; 57 deg within 2 s with no feedback | S-Py |
| Complementary filter, C code in desktop FreeRTOS simulation | RMS estimate error 0.71 deg (roll), 0.77 deg (pitch); max 1.7 / 2.9 deg over 99.5 s | S-C (`filter.json`) |
| Filter on synthetic sensors (0.1 deg/s gyro bias, +-0.1 m/s^2 accel noise) | RMS error: accel 0.34, gyro 0.81, fused (gamma 0.9) 0.08, fused (gamma 0.9992) 0.39 deg | S-Py |
| Hardware: controller oscillated in roll; pitch offset about 30 deg; yaw drifting | read off report Fig. 7 (approximate, +-7 deg roll peaks) | R |
| Embedded Coder port not completed | stated in report sections VIII and IX | R |

The pulse amplitude, kick size and timing are our choice (`analysis/scenario.py`). The report does not give them. Report
Fig. 5 shows a rise time of roughly one second without overshoot, which is the same shape, but I did not extract numbers
from that figure.

The C-simulation run is real output of `firmware/filter.c` and `firmware/controller.c`, but the plant in it is the course
template's dynamic model and the controller there uses the gain K hard-coded in `controller.c`. It is not the hardware.

## Hardware result (report Fig. 7)

`media/report_fig7_hardware.png` is a crop of the report figure. It is not regenerated by a script, and the raw log is not
available to me. (`simulink/` in the course repo holds a `FlightData.mat`, but it is dated 2020 and is the course
template's data, so I did not use it.)

What the figure shows, read by eye:

- Roll (red) oscillates continuously, about +-5 to +-7 deg peak, for the whole logged window.
- Pitch (green) sits near 30 deg for most of the run and falls off at the end.
- Yaw (blue) drifts from about 8 to 15 deg.

The report names a battery on top of the frame (uneven weight) as a probable cause and says the battery drained
unusually fast. It does not run an experiment to separate causes.

## Mismatches found while reproducing

1. **Gain K vs. the report.** With the report's equations (18), Q, R and Ts, `dlqr` gives row 1 of K as
   `[-0.0224 -0.0089 -0.0332 -0.0132 -0.0569]`; the report (eq. 25) prints `[-0.0284 -0.0112 -0.0420 -0.0166 -0.0701]`.
   Sign pattern is identical; magnitudes differ by 23-27 %. Scaling B by 0.79 (roll/pitch rows) and 0.80 (yaw row)
   reproduces eq. 25 to 8e-5, which suggests the Simscape-linearised B was about 20 % smaller than the hand-derived one.
   I found no physical reason for that factor, so the figures use the hand-derived B and say so.
   <!-- TODO(owner): do you know what differed in the Simulink linearisation (units, thrust model, an extra gain)? -->
2. **K in `controller.c` is a third set**, e.g. row 1 `[-0.0198 -0.0020 -0.0203 -0.0024 -0.0067]`. It was retuned in the C
   commits ("new Gain K"), and the rate and yaw-rate gains differ a lot from the report. The C code feeds `K` in
   radians and converts the result to PWM with `pwm_n`.
3. **Filter gamma.** The report uses gamma = 0.9. `filter.c` computes `gamma = alpha / (h + alpha)` with alpha = 6 and
   h = 0.005 s, which is 0.9992 (time constant about 6 s), so the gyro dominates almost completely. The comment next to
   `h` still says "10 ms". On the synthetic test gamma = 0.9 has the lower error, but 0.9992 is what ran in the C simulation.
4. **Yaw estimate.** `filter.c` sets the yaw estimate to 0, and the controller feeds back yaw rate only. This matches
   the report ("yaw angle is not stabilised") but means no yaw angle is estimated in C.
